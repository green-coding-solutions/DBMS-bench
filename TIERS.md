# Configuration tiers for the EDBT 2027 paper

Branch `t2-new` forks from `t0` (pinned images, warm-up phase split) and applies
**T2: workload-tuned for throughput** to every scenario. Envelope: 4 CPU / 8192 MB per DBMS
container (H1); Oracle Database Free is evaluated at min(envelope, 2048 MB licence cap).
Generated by `scripts/dbms_bench_tier_branch.py` of the paper repository from the knob tables in
`scripts/tier_knobs.py`; do not edit the scenario files by hand, change the tables and regenerate.

## Definitions

- **T1, resource-sized and workload-blind**: only parameters whose vendor-documented recommended
  value is a function of memory size or CPU count, evaluated at the cgroup envelope. It is the
  configuration a container image could derive by itself from its cgroup limits at start-up.
- **T2, workload-tuned for throughput**: one configuration per workload class. `oltp` = TPC-C,
  YCSB, Wikipedia; `olap` = TPC-H; `htap` = CH-benCHmark (oltp settings plus the olap query-memory
  and parallelism settings; parallelism conflicts resolve to olap, checkpointing conflicts to oltp).
  PostgreSQL uses the PGTune profile of the class (oltp, dw, mixed). The other engines use the
  HammerDB best-practice pages for TPROC-C and TPROC-H, with memory sizes from the T1 rule because
  those pages were written for hosts with hundreds of gigabytes, and with Oracle's documented PGA
  split. Both tiers keep durability and page integrity exactly as shipped (plan.md 0.3 rule 2).
- Schema, indexes, storage engine, scale factor, client count and driver scripts are identical to
  `t0`; the TPC-H driver keeps its degree of parallelism of 2 in every tier.

## How a tier is applied and verified

| Engine | Mechanism | Verification in the run log |
|---|---|---|
| PostgreSQL | `postgres -c name=value ...` as the service `command` | `Configure DBMS` step prints `CONFIG name=value` from `pg_settings` |
| MariaDB, MySQL | `--name=value ...` as the service `command` (the entrypoint passes them to the server) | same, from `global_variables` |
| SQL Server | `Configure DBMS` step runs `db/mssql/tiers/*.sql` through `sqlcmd -b` (sp_configure, ALTER SERVER CONFIGURATION, ALTER DATABASE model); all dynamic | prints before and after values from `sys.configurations`, scheduler count, tempdb files |
| Oracle | `Configure DBMS` step runs `db/oracle/tiers/*.sql` through `sqlplus / as sysdba` (ALTER SYSTEM ... SCOPE=SPFILE, redo log groups, SHUTDOWN IMMEDIATE, STARTUP, about 10 s), then waits until FREEPDB1 answers through the listener | prints before and after values from `v$parameter`, `v$log`, `v$sga` |

The step is the first flow step of every scenario, before the schema build and outside the
measured phase. `scripts/validate_tier_config.py` in the paper repository compares the printed
values with the tables below for every fetched run.

## Findings while building the tiers (5 September 2026, local, pinned images, H1 envelope)

- MySQL 26.7 `innodb_dedicated_server=ON` sized the buffer pool from the host's 33 GB, not from
  the 8 GB cgroup (24.9 GB pool; MySQL bug 90231). The new `container_aware=ON` switch (off by
  default) makes the same rule read the cgroup and yields exactly the T1 values (6144M pool, 2G redo).
- SQL Server 2025 reads the cgroup: it reports 6554 MB of RAM (80 percent of 8 GB), targets a
  5752 MB buffer pool and creates five tempdb data files for the five CPUs of the cpuset. Its
  memory and tempdb are therefore already resource-sized at T0; T1 only aligns MAXDOP and the
  scheduler count with the 4-CPU quota, as Microsoft documents for cgroup v2.
- Oracle Database Free ships with SGA 1536M + PGA 512M = the full 2048 MB cap; T1 can only move
  the split to Oracle's documented 80/20 (sga_max_size must be a multiple of the 16 MB granule
  and SGA + PGA at most 2048 MB, otherwise ORA-56752).
- Oracle Database Free forces `parallel_max_servers` back to 1 at every startup, even when the
  spfile says 4, so the edition executes no parallel query; HammerDB's degree of parallelism 2
  for TPC-H is nominal on this engine and the T2 olap tier cannot change that.
- PostgreSQL 18 cannot use `io_method=io_uring` inside Docker (seccomp: Operation not permitted),
  so PGTune's io_uring recommendation is dropped and the default `worker` method stays.
- Huge pages are unavailable inside the containers (`huge_pages_status=off`), for every engine.

- `mssql-maxdop`: Microsoft Learn, "Server configuration: max degree of parallelism": single NUMA node with at most eight logical processors, keep MAXDOP at or under the number of logical processors

- `oracle-pga`: Oracle Database 23ai Performance Tuning Guide, "Tuning the Program Global Area": OLTP PGA_AGGREGATE_TARGET = 20 percent, DSS = 50 percent of the memory available to the instance
- `oracle-fsio`: Oracle Database 23ai Reference, FILESYSTEMIO_OPTIONS: SETALL enables both asynchronous and direct I/O on file system files
- `oracle-free-cap`: Oracle Database Free licence: at most 2 GB of memory for SGA and PGA and 2 CPU threads (verified: ORA-56752 when SGA + PGA exceed 2048 MB)
- `redo-analogy`: Redo log capacity for Oracle follows the InnoDB redo rule of T1 (2 GB for 4 CPUs) in three groups; Oracle's Administrator's Guide gives no size rule beyond "test different configurations"
